# Documentation & Heading Anchor Rules

When composing, reviewing, or refactoring user documentation, guides, or README files across the monorepo (e.g., `packages/tempo/doc/`, `packages/plugins/*/doc/`, and `README.md` files):

## 1. Plugin Documentation Source of Truth (CRITICAL)
- **NEVER edit files directly in `packages/tempo/doc/9-plugins/`**: That directory is a build artifact auto-harvested from `packages/plugins/<plugin-name>/doc/` during documentation build (`npm run docs:build` via `harvest-plugins`).
- **Always edit plugin documentation in its source package**: e.g., `packages/plugins/celestial/doc/lunar.md`, `packages/plugins/ticker/doc/index.md`, etc.
- Any direct edits made to `packages/tempo/doc/9-plugins/` will be overwritten and lost.

## 2. VitePress Heading Slug & Anchor Mismatch Guardrails

The public documentation site (GitHub Pages) is built with **VitePress**. VitePress generates heading anchors differently than GitHub’s markdown viewer. Always adhere to these rules when creating or linking to headings:

### A. Numbered Headings (Leading-Digit Prefix `_`)
- VitePress prepends an underscore (`_`) to any heading starting with a number so that the HTML `id` is a valid CSS identifier.
  - `## 1. Lazy Evaluation` → Anchor is `#_1-lazy-evaluation` (NOT `#1-lazy-evaluation`)
  - `## 4.1 Dynamic Context` → Anchor is `#_4-1-dynamic-context` (NOT `#4-1-dynamic-context`)
  - `## 5. Development Constraints` → Anchor is `#_5-development-constraints` (NOT `#5-development-constraints`)

### B. Emojis in Headings
- VitePress **preserves emojis** in generated heading slugs, whereas GitHub strips them.
  - `## ⚡ Quick Start` → Anchor is `#⚡-quick-start` (NOT `#quick-start`)
  - `## 🛠️ Custom Format Tokens` → Anchor is `#🛠️-custom-format-tokens` (NOT `#custom-format-tokens`)
- When linking to a heading containing an emoji, include the emoji in the anchor, or prefer custom anchor IDs (`{#custom-id}`).

### C. Punctuation & Code Identifiers (`.` and `&`)
- **Dots in code spans** are converted to hyphens (`-`), not deleted.
  - `#### \`Ticker.Snapshot\`` → Anchor is `#ticker-snapshot` (NOT `#tickersnapshot`)
  - `## Explicit Initialization (\`Tempo.init\`)` → Anchor is `#explicit-initialization-tempo-init` (NOT `#explicit-initialization-tempoinit`)
- **Ampersands & Whitespace**: VitePress collapses consecutive dashes into a single dash (`-`).
  - `### Format Modifiers & Localization` → Anchor is `#format-modifiers-localization` (NOT `#format-modifiers--localization`)

## 2. Best Practice: Explicit Custom Anchors `{#id}`
- For important sections, numbered headings, or headings with complex characters/emojis that will be linked to from other pages, use VitePress's native custom anchor syntax:
  ```markdown
  ## 3. Explicit Initialization (`Tempo.init`) {#explicit-initialization}
  ```
- This guarantees stable anchors that will not break even if section numbers, emojis, or punctuation are updated later.

## 3. Plugin Documentation Source of Truth
- **Never edit files directly in `packages/tempo/doc/9-plugins/`**: That directory is wiped and harvested automatically from `packages/plugins/<plugin-name>/doc/` during `npm run docs:build`.
- Always edit plugin documentation inside its source package directory (e.g. `packages/plugins/ticker/doc/index.md`).

## 4. Pre-Commit Validation
- Before committing changes to documentation files, verify that all internal links with anchors (`#...`) resolve to valid IDs generated by the VitePress markdown renderer.

## 5. Prohibit Self-Referential & Trivial Viewport Links
- **No Self-Referencing Headings**: Never create a link pointing to the enclosing section or parent heading the reader is currently in (e.g., linking `[Range-Keys](#_5-development-constraints)` from within `## 5. Development Constraints`).
- **No Trivial Intra-Section Jumps**: Avoid intra-page anchor links that only shift the viewport a few lines within the same paragraph or immediately visible block. Refer directly in plain text instead (e.g., "This rule...", "As noted above...").
- **Legitimate Exceptions**: 
  - Top-of-page Table of Contents / Quick-Jump navigation outlines.
  - Type cross-references jumping past lengthy code blocks or implementation examples to a type definition table below.

## 6. Prefer Literal Unicode Characters Over HTML Entities
- **Always use literal Unicode characters** (e.g., `→`, `←`, `•`, `✓`, `—`, `–`) instead of HTML entities (e.g., `&rarr;`, `&larr;`, `&bull;`, `&check;`, `&mdash;`, `&ndash;`).
- **Rationale**:
  - **Cross-Platform Consistency**: Native UTF-8 characters render reliably everywhere—on npmjs.com, VitePress (GitHub Pages), GitHub Flavored Markdown (GFM), IDE markdown previews, and terminal/CLI pagers.
  - **Avoid Sanitizer Mangling**: HTML entities risk double-escaping (`&amp;rarr;`) or displaying as unrendered raw entity text depending on the sanitizer or markdown environment.
  - **Clean Slugs & Code Spans**: Prevents entity text from leaking into VitePress anchor generation or code spans.

## 7. Mathematical & Algorithmic Notation (MathJax 3)
- **VitePress Math Support**: The documentation site has native MathJax 3 enabled (`markdown.math: true` via `markdown-it-mathjax3` with `90%` font scaling in `custom.css`).
- **Context-Specific Standards**:
  - **Documentation Prose (`packages/tempo/doc/**`)**: Format Big-O notation and inline math using single dollar signs: `$O(1)$`, `$O(N)$`, `$O(0)$`, `$O(\log n)$`.
  - **Standalone / Multiline Equations**: Use double dollar signs (`$$...$$`) on their own lines:
    ```markdown
    $$
    \Delta = T_{\text{server}} - \left(T_{\text{client}} + \frac{\text{RTT}}{2}\right)
    $$
    ```
  - **README Files (Published to npmjs.com & GitHub Roots)**: Use inline code backticks (`` `O(1)` ``) or plain text. npmjs.com uses sanitized GFM without MathJax, so code backticks ensure clean, badge-like rendering across npm without raw dollar signs.
  - **Inside Code Blocks & Source Comments (`// ...`, `/* ... */`)**: Code blocks and comments are never parsed by MathJax. Always use plain text `O(1)` or `O(N)` without dollar signs so IDE hover tooltips, JSDoc, and syntax highlighters do not display raw formatting characters.
- **Dollar Sign Conflict Prevention Guardrails**:
  - *Do NOT use `$$...$$` for inline expressions*: Double dollar signs render as **display/block-level formulas** and will break the text line into a separate centered block.
  - **Code Identifiers in Backticks**: Always wrap symbol properties, discovery keys, and code variables in backticks (e.g., `` `$Target` ``, `` `$Tempo` ``, `` `$updateScopeStatus` ``). MathJax automatically ignores code spans.
  - **Currency & Prose Dollar Signs**: In regular prose outside code spans, escape literal dollar signs as `\$` (e.g., `\$0 cost`) or wrap in backticks (`` `$0` ``) to prevent unintentional delimiter pairing.
- **Physical Quantities & Simple Unicode**: For simple unit exponents, degrees, and common operators, prefer plain Unicode characters (`°`, `≈`, `×`, `²`, `³`, `√`, `Δ`, `≤`, `≥`, `±`).
