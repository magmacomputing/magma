# Discussion: Supporting Calendar Weeks with a Different Length

## Purpose

This note records the current seven-day assumptions in Tempo and the related API
surface to review if Tempo ever considers calendars whose weeks do not contain
seven days. It is a discussion and investigation guide, not a proposal to change
current behavior.

The current implementation is built around the ISO/Gregorian seven-day week.
Locale configuration can change the first day of a week and identify weekend
days, but it does not change the number of days in a week. Temporal's calendar
API has a `daysInWeek` concept, but commonly supported calendars currently
report seven; confirm the runtime and polyfill support before relying on it.

## Direct seven-day assumptions in `src/`

### Weekday arithmetic and week boundaries

| Location | Current assumption |
| --- | --- |
| [`engine/engine.term.ts`](../src/engine/engine.term.ts#L43) | `DAYS_IN_WEEK = 7` drives relative weekday shifts (`next Monday`, `last Friday`, and repeated weekday modifiers). |
| [`engine/engine.lexer.ts`](../src/engine/engine.lexer.ts#L252) | Ordinal weekday resolution uses modulo 7 to find the first or last occurrence of a named weekday in a month, then offsets by whole weeks. |
| [`module/module.mutate.ts`](../src/module/module.mutate.ts#L354) | `start:week` uses Monday by default or the locale's `firstDay`; the locale calculation wraps with modulo 7. |
| [`module/module.mutate.ts`](../src/module/module.mutate.ts#L380) | `mid:week` uses Thursday by default or the locale week start plus three days. This encodes a seven-day midpoint. |
| [`module/module.mutate.ts`](../src/module/module.mutate.ts#L407) | `end:week` uses Sunday by default or adds seven days after the locale week start. ISO-week aliases are explicitly Monday-through-Sunday. |

These are calendar-week behaviors, distinct from adding or subtracting a
duration. Changing only a shared constant would not be enough: weekday numbering,
the weekday names, locale week metadata, and the meaning of the week boundaries
would also need to agree.

### Formatting and week numbering

| Location | Current assumption |
| --- | --- |
| [`module/module.format.ts`](../src/module/module.format.ts#L315) | `{ww}`, `{woy:cal}`, `{woy:month}`, and `{wom}` form seven-day buckets by dividing day-of-month or day-of-year by 7. These are bucket/ordinal formats, not all the same kind of week numbering. |
| [`module/module.format.ts`](../src/module/module.format.ts#L388) | `{dd:week}` / `{day:week}` and `{dow}` zero-based forms wrap Sunday to zero with modulo 7. |
| [`module/module.format.ts`](../src/module/module.format.ts#L395) | `{dow:locale}` uses the locale's first day and modulo 7 to produce a 1-based locale-relative weekday. |
| [`module/module.format.ts`](../src/module/module.format.ts#L414) | `{wkd}` and `{www}` map the date's weekday number to fixed English weekday-name enums (or localized formatting paths). |
| [`tempo.type.ts`](../src/tempo.type.ts#L214) | `woy` is statically limited to 1–53, and `wkd` is statically limited to 1–7. |
| [`tempo.type.ts`](../src/tempo.type.ts#L257) | The `dow`, `wkd`, and `www` format tokens expose numeric/name weekday concepts; adding a `{diw}` token would require updating this token registry as well as runtime formatting. |

`{woy}` / `{yow}` ISO week-of-year behavior is implemented separately from
seven-day bucket formatting. `getISOWeekOfYear` is used by the getters,
formatter, and mutations, and represents ISO week numbering; it should not be
silently reinterpreted as a variable-length calendar week. Locale week-of-year
formatting is also separate: its locale rules change week start/minimal days,
not week length.

### Weekday model and lookup data

| Location | Current assumption |
| --- | --- |
| [`support/support.enum.ts`](../src/support/support.enum.ts#L179) | `WEEKDAY` and `WEEKDAYS` enumerate the seven Gregorian weekday names, Monday=1 through Sunday=7. Parser and formatter lookups depend on these enums. |
| [`support/support.util.ts`](../src/support/support.util.ts#L269) | Localized weekday names are generated by formatting seven consecutive dates and assigning numbers 1–7. |
| [`tempo.class.ts`](../src/tempo.class.ts#L1428) | `www` and `wkd` map `dayOfWeek` into the fixed weekday enums. |
| [`tempo.class.ts`](../src/tempo.class.ts#L1430) | `dow` exposes the ISO-style weekday number (Monday=1, Sunday=7). |
| [`engine/engine.lexer.ts`](../src/engine/engine.lexer.ts#L225) | Ordinal weekday parsing resolves names through the same fixed weekday enums. |

The getter/token set has no `diw` (days in week) today. Adding that getter and
format token could expose the underlying calendar's value, if available, but
would not make the existing weekday numbers, names, parsing, week arithmetic,
or week-numbering algorithms support a non-seven-day week.

## Related but intentionally separate: fixed-duration weeks

| Location | Current behavior |
| --- | --- |
| [`module/module.duration.ts`](../src/module/module.duration.ts#L69) | `balance({ nominal: true })` converts a week to seven days. It also uses approximate 30-day months and 365-day years, so this is nominal arithmetic rather than calendar-aware balancing. |
| [`support/support.enum.ts`](../src/support/support.enum.ts#L64) | The fixed duration constant is 604,800 seconds per week. |
| [`support/support.enum.ts`](../src/support/support.enum.ts#L103) | The fixed duration constant is 604,800,000 milliseconds per week. |

These values describe a fixed-duration week of 7 × 24 hours, not necessarily
the behavior of a calendar's week unit. Calendar operations such as
`Temporal.ZonedDateTime.add({ weeks: 1 })` can be wall-calendar operations;
around daylight-saving transitions, a local calendar week need not be exactly
604,800 elapsed seconds. A future design should state whether it changes
calendar week arithmetic, fixed-duration constants, nominal balancing, or some
combination.

## API, token, and compatibility gotchas

- **`dow` is not locale-relative.** The getter and plain `{dow}` token are
  ISO-style numbers. `{dow:locale}` is a locale-relative display option, and
  `t.intl.info.firstDay` / `weekend` are locale metadata. None currently
  specifies a different week length.
- **Weekday strings are not arbitrary calendar day labels.** The fixed weekday
  enums, localized weekday-name generation, parser, and `wkd`/`www` getters
  assume seven positions. Review all of them together if numbering or names can
  differ by calendar.
- **Week number is not `daysInWeek`.** `woy` and `yow` refer to ISO week-year
  rules; `{woy:locale}` uses locale week rules. `{ww}`, `{wom}`, and calendar
  week buckets have separate semantics. Their names and current behavior should
  not be assumed to map to a future calendar's native week fields.
- **Types and token validation are part of the public API.** Update `wkd`,
  possibly `woy`, `TempoFormatTokens`, getter types, documentation, and tests
  together. Avoid widening types to arbitrary numbers unless runtime semantics
  and validation are defined.
- **Temporal support is a dependency boundary.** Verify that the Temporal
  implementation used by Tempo exposes calendar-sensitive `daysInWeek` and
  defines `dayOfWeek`, week addition, and week-number fields in the way the
  proposed behavior needs. Do not infer this from calendar support alone.
- **Locale and calendar are independent inputs.** A locale may set the first
  weekday and weekend without changing the calendar's week length. Calendar
  awareness should be explicit rather than derived from locale settings.
- **Compatibility may be observable.** Current callers may rely on Sunday=7,
  Monday=1, seven-day relative weekday shifts, ISO week results, and nominal
  week balancing. Any changed behavior needs compatibility policy and
  regression coverage.

## Questions to resolve before implementation

1. Is the goal only to expose `daysInWeek` (for example via `diw`), or to make
   Tempo's date arithmetic and parsing truly support calendars with a different
   week length?
2. Which calendars and Temporal implementations must work? Can any such
   calendar actually be represented by the Temporal/calendar adapter in the
   supported runtime?
3. What is the meaning and numbering of weekdays in the target calendar?
   Can weekday names be obtained from `Intl`, or does the calendar need its own
   names and parser aliases?
4. Which APIs are calendar-week operations versus explicitly ISO-week
   operations? Should existing `dow`, `woy`, `yow`, and week aliases retain
   their current ISO meaning?
5. Should `week` in `Tempo.Duration` remain exactly seven days while
   calendar-week arithmetic varies, or should duration normalization also
   become calendar-aware and require a `relativeTo` date?
6. Should `{ww}`, `{wom}`, and `{woy:cal}` remain seven-day buckets, or be
   redefined? If unchanged, clearer token names or documentation may be needed.
7. What compatibility/versioning policy applies to changes in weekday
   getters, tokens, modifiers, locale week boundaries, and term parsing?

## Suggested investigation and test coverage

If this work is pursued, first prototype against the intended Temporal calendar
and runtime. Then test at least:

- Getter/token consistency for the week length and weekday value/name.
- Start, midpoint, and end of week under both ISO and locale week starts.
- Forward/backward and repeated weekday parsing, including ordinal weekdays
  within a month.
- Week-of-year/week-year behavior at year boundaries, keeping ISO and locale
  variants explicit.
- Week bucket tokens and zero-based/localized weekday formatting.
- Duration balancing separately from calendar-week addition, including
  daylight-saving transitions for zoned dates.
- Type-level format validation, public documentation, and regression tests for
  existing seven-day behavior.
